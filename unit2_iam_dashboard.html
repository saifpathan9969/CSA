Mission Statement CORE OBJECTIVE

Implement an enterprise-grade IAM security architecture using Terraform IaC, enforcing the Principle of Least Privilege across three distinct user groups, with MFA mandatory at the session level and zero static credentials on compute.

  • ▶ Three IAM Groups: Admins / Developers / Auditors
  • ▶ MFA enforced via Explicit Deny + BoolIfExists condition
  • ▶ EC2 accesses S3 via Instance Profile — no hardcoded keys
  • ▶ S3 bucket enforces KMS encryption + TLS-only access
  • ▶ Aligns with CIS AWS Foundations Benchmark v1.4.0

Why BoolIfExists, not Bool?
Bool would also block service-to-service API calls where MFA context
is simply absent (not false). BoolIfExists only triggers when the key
is explicitly present and set to false — protecting human sessions only.

* Except: iam:CreateVirtualMFADevice, iam:EnableMFADevice, iam:ListMFADevices, iam:ResyncMFADevice, iam:GetUser, iam:ChangePassword
The Bootstrap Problem SOLVED

A naive MFA-everywhere policy creates a circular deadlock: new users can't log in to set up MFA because the policy blocks them before they can enroll.

WITHOUT bootstrap exception:
New user logs in → No MFA device → Policy denies iam:CreateVirtualMFADevice → User cannot set up MFA → PERMANENT LOCKOUT
WITH NotAction bootstrap exception:
New user logs in → Deny applies to all actions except 6 MFA setup actions → User can enroll MFA device → Session now has MFA token → Full access restored
IAM Policy Evaluation Priority EVALUATION ORDER
1. Explicit DENY  ← EnforceMFAPolicy uses this
2. SCPs (Service Control Policies)
3. Resource-based Policies
4. Identity-based Policies (Allow)
5. Session Policies
6. Implicit DENY (default)

Explicit Deny at step 1 always overrides any Allow further down the chain. No group Allow policy can bypass it.

EnforceMFAPolicy — JSON POLICY DOCUMENT 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowSelfServiceMFASetup",
      "Effect": "Allow",
      "Action": [
        "iam:ListVirtualMFADevices", // ← view enrolled devices
        "iam:CreateVirtualMFADevice", // ← create TOTP seed
        "iam:EnableMFADevice",        // ← bind device to user
        "iam:ResyncMFADevice",         // ← fix clock drift
        "iam:GetUser",                 // ← read own metadata
        "iam:ListMFADevices",          // ← check enrollment
        "iam:ChangePassword"           // ← first login reset
      ],
      "Resource": [
        "arn:aws:iam::*:mfa/${aws:username}",  // ← OWN device only
        "arn:aws:iam::*:user/${aws:username}"  // ← OWN user only
      ]
    },
    {
      "Sid": "DenyAllExceptMFASetupWithoutMFA",
      "Effect": "Deny",          // ← Explicit Deny — wins everything
      "NotAction": [              // ← bootstrap exceptions survive
        "iam:CreateVirtualMFADevice",
        "iam:EnableMFADevice",
        "iam:ListMFADevices",
        "iam:ResyncMFADevice",
        "iam:GetUser",
        "iam:ChangePassword"
      ],
      "Resource": "*",
      "Condition": {
        "BoolIfExists": {         // ← only fires on human sessions
          "aws:MultiFactorAuthPresent": "false"
        }
      }
    }
  ]
}

Why NOT Static Access Keys ANTI-PATTERN
Common attack vectors with hardcoded keys:
  • ✗ Keys committed to Git history — public forever
  • ✗ Keys in Docker images — extracted with docker history
  • ✗ Keys in .bashrc — stolen on any host compromise
  • ✗ No automatic expiry — valid until manually rotated
  • ✗ No MFA requirement — works from any IP, any time
  • ✗ Hard to rotate across 100+ deployment targets
Instance Profile Advantages BEST PRACTICE
Security properties:
  • ✓ Zero credentials on disk, in env vars, or in code
  • ✓ Temporary STS tokens (max 1 hour session duration)
  • ✓ Auto-refreshed by AWS SDK — zero downtime rotation
  • ✓ IMDSv2 — SSRF attacks cannot steal credentials
  • ✓ Hop limit 1 — container escape prevented
  • ✓ On termination, credentials are automatically revoked
  • ✓ CloudTrail logs every sts:AssumeRole call
Trust Policy — JSON EC2S3AccessRole 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "EC2AssumeRole",
      "Effect": "Allow",
      "Principal": {
        "Service": "ec2.amazonaws.com"  // ← ONLY EC2 can assume this role
      },
      "Action": "sts:AssumeRole"         // ← grants temporary credentials
    }
  ]
}

// IMDSv2 Terraform configuration:
metadata_options {
  http_endpoint               = "enabled"
  http_tokens                 = "required"   // ← enforces IMDSv2
  http_put_response_hop_limit = 1           // ← blocks container escape
  instance_metadata_tags      = "enabled"
}
S3 Hardening KMS + TLS + Block Public
🔐

SSE-KMS Encryption at Rest

All objects encrypted with Customer Managed Key alias/csa-unit2-s3-key. Bucket rejects uploads without x-amz-server-side-encryption: aws:kms header. KMS key rotation enabled annually. CIS 2.1.2.

🔒

TLS-Only Enforcement

Bucket policy issues Explicit Deny on all s3:* actions where aws:SecureTransport = false. HTTP connections are rejected at the resource level. CIS 2.1.1.

🚫

Public Access Block (All 4 Flags)

BlockPublicAcls, BlockPublicPolicy, IgnorePublicAcls, RestrictPublicBuckets — all set to true. No public exposure possible. CIS 2.1.5.

📜

Versioning Enabled

Object versioning preserves every write. Accidental deletes or ransomware overwrites can be recovered. Provides immutable audit trail of all object versions.

📋

Server Access Logging

All S3 requests logged to a separate csa-secure-audit-bucket-prod-access-logs bucket. Log bucket also has SSE-KMS and all public access blocked. Logs feed into GuardDuty and CloudTrail.

🔑

KMS Key Rotation

Automatic annual key rotation enabled on the CMK. Old key material retained for decryption of existing objects. Deletion window: 30 days. Bucket key enabled to reduce KMS API costs.

S3 Bucket Policy — Core Statements RESOURCE-LEVEL ENFORCEMENT 
{
  "Statement": [
    {
      "Sid": "EnforceTLSRequestsOnly",
      "Effect": "Deny",
      "Principal": "*",              // ← applies to ALL principals
      "Action": "s3:*",
      "Condition": {
        "Bool": { "aws:SecureTransport": "false" }  // ← HTTP rejected
      }
    },
    {
      "Sid": "DenyUnencryptedObjectUploads",
      "Effect": "Deny",
      "Action": "s3:PutObject",
      "Condition": {
        "StringNotEquals": {
          "s3:x-amz-server-side-encryption": "aws:kms"  // ← must use KMS
        }
      }
    },
    {
      "Sid": "AllowEC2RoleAccess",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::ACCOUNT:role/EC2S3AccessRole" },
      "Action": [ "s3:GetObject", "s3:PutObject", "s3:DeleteObject", "s3:ListBucket" ]
    }
  ]
}

Quick Start Commands DEPLOYMENT 
# Navigate to unit2 directory (completely separate from Unit 1)
cd terraform/unit2_iam

# Download AWS provider plugin
terraform init

# Preview all resources that will be created
terraform plan -out=unit2.tfplan

# Apply infrastructure
terraform apply unit2.tfplan

# Override user lists at plan time:
terraform plan \
  -var='admin_usernames=["alice","bob"]' \
  -var='developer_usernames=["charlie","diana","eve"]' \
  -var='auditor_usernames=["frank"]' \
  -var='project_bucket_name=my-org-secure-bucket'

# Verify deployment
aws iam list-groups --path-prefix /csa-unit2/
aws iam get-role --role-name EC2S3AccessRole
aws s3api get-bucket-encryption --bucket csa-secure-audit-bucket-prod
